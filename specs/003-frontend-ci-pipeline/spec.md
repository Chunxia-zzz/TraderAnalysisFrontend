# Feature Specification: 前端仓库接入 CI 流水线

**Feature Branch**: `003-frontend-ci-pipeline`

**Created**: 2026-11-04

**Status**: Implemented — 本地与远端均已验证（CI 首跑 38s 全绿，反向验证 4 组通过；见 `tasks.md` §验证记录）

**Input**: User description: "为我的前端仓库加上CI流程，前端仓库的本地地址在：F:\TraderAnalysisFrontend，如果有可能。在添加CI流程时请遵循spec-kit原则"

## 背景

> ⚠️ **后续变更（2026-11-04）**：本 spec 决策记录里的「不含部署（CD）」**已由 `specs/004-deploy-on-green/` 取代**。
> 003 交付的 `check` job 与 `dist-<sha>` artifact 正是 004 的部署前提；原文保留以记录当时的范围判断。

前端仓库目前**没有任何自动化门禁**：`npm run build` 只在本地手动跑，`git push` 之后无人复核。
后果已经发生过——「文档点名了不存在的文件」「路由挂载了但页面白屏」这类问题，全靠人工记得跑一遍才发现
（见 constitution §五 的记录：`KLineChart.vue`、`Login.vue` 两次踩坑）。

后端仓库 `F:\TraderAnalysis` 已有 CI（`.github/workflows/ci.yml`：lint + 测试 + 覆盖率门禁 + 密钥扫描，
本地 `scripts/check.sh` 与 CI 同源）。本次是**把同一套纪律搬到前端**，不是发明新流程。

前端与后端的差异必须正视：**前端当前没有 lint 配置、没有一条单元测试**。
所以本次不只是「接一条流水线」，还要先补齐被流水线检查的东西——否则接上去第一天就是红的，
红久了门禁就会被忽略，等于没接。

## 决策记录（已与用户确认）

| 问题 | 决定 | 理由 |
|---|---|---|
| 门禁范围 | **构建 + ESLint + 单元测试 + 密钥扫描** | 用户明确选择最完整的一档；只跑 build 抓不到规范与逻辑回归 |
| 是否含部署（CD） | **不含，保持现有 `git push` 到 bare repo 的部署路径** | 引入 SSH 私钥与第二条部署路径，风险与收益不对等；有真实部署目标前不建空转的部署 job |
| 是否做覆盖率门禁 | **不做** | 前端覆盖率主体是组件渲染，纯单测只覆盖 api/util 薄层。在个位数覆盖率上设阈值是假门禁，只会制造噪音 |
| 是否引入 Prettier | **不做** | ESLint 已覆盖可判定的问题；引入格式化会全库重排 6588 行源码，改动面与收益不成比例 |
| 是否跑现有 `smoke-*.mjs` | **不跑** | 它们依赖本机 Chrome CDP + 前端 5173 + 后端 8000，CI 里跑必然超时。仍留在本地质量门（constitution §三） |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 推送即体检，坏提交当场红 (Priority: P1)

开发者把改动推到 `main`，几分钟内在 GitHub 上看到一次明确的结论：依赖能否按锁文件装好、
代码是否符合规范、单元测试是否通过、生产构建能否产出 `dist/`。
任何一步失败，页面直接指出是**哪一步**红的，而不是只有一句 CI failed。

**Why this priority**: 这是本需求的原始动机——把「我记得本地跑一下」变成「机器每次都跑」。没有它，其余都是附加。

**Independent Test**: 在 `main` 上推一个正常提交，观察流水线全绿；再推一个故意写坏的提交，观察对应步骤变红且后续步骤不再执行。

**Acceptance Scenarios**:

1. **Given** 仓库收到 `main` 的推送，**When** 流水线运行，**Then** 依次执行「锁文件安装 → 代码规范检查 → 单元测试 → 生产构建」，四步全绿才算通过
2. **Given** 代码里存在语法错误，**When** 构建步骤执行，**Then** 该步骤失败，流水线整体判红，且失败信息定位到具体文件
3. **Given** 代码违反已启用的规范规则，**When** 规范检查步骤执行，**Then** 该步骤失败并列出违规位置，不再继续执行单测与构建
4. **Given** 单元测试有断言失败，**When** 测试步骤执行，**Then** 该步骤失败并给出失败用例名

---

### User Story 2 - 本地预检与 CI 同源 (Priority: P1)

开发者在 `git push` 之前跑一条命令，得到与 CI **完全一致**的结论。
不存在「本地跑的是 A 套、CI 跑的是 B 套」，也不存在「本地绿、CI 红」。

**Why this priority**: 门禁的价值取决于它可被提前满足。本地没有等价命令时，CI 就退化成事后审判，开发者只能靠反复推送试错。

**Independent Test**: 本地故意制造一处规范违规，运行预检命令 → 失败；修复后重跑 → 通过；同一次改动推送后 CI 结论与本地一致。

**Acceptance Scenarios**:

1. **Given** 依赖已安装，**When** 开发者运行预检命令，**Then** 依次执行与 CI 相同的检查项，任一项失败即非零退出
2. **Given** 本地预检通过，**When** 同一提交被推送，**Then** CI 也通过（除非环境差异，且差异必须能被解释）
3. **Given** 开发者只记得一条命令，**When** 查看 `README.md` 与 `AGENTS.md`，**Then** 能找到这条命令及其与 CI 的对应关系

---

### User Story 3 - 密钥不进仓库 (Priority: P2)

每一次推送都做一次密钥扫描；历史提交里若混入过密钥，也能被发现。
扫描失败是**独立信号**，不会因为其他步骤通过而被掩盖。

**Why this priority**: 这个仓库有 `.env.development` / `.env.production` 实体文件（已 ignore，但存在于工作区）。
一次误提交就会把后端地址或凭据推上 GitHub，且 git 历史无法简单撤回。

**Independent Test**: 在临时分支提交一个带明显密钥格式的文本文件，推送后观察密钥扫描 job 变红；删除该提交后恢复绿色。

**Acceptance Scenarios**:

1. **Given** 一次普通推送，**When** 流水线运行，**Then** 存在一次对**完整提交历史**的密钥扫描
2. **Given** 提交内容里含有疑似密钥，**When** 扫描执行，**Then** 该 job 失败并在日志中指出文件与行
3. **Given** 主检查流水线全绿但密钥扫描失败，**When** 查看运行结果，**Then** 整体结论仍为失败

---

### User Story 4 - 纯文档改动不浪费流水线 (Priority: P3)

只改 `README.md` 或 `docs/`、`specs/` 下的文件时，流水线不启动。

**Why this priority**: 本仓库文档密度高，文档提交频繁。每次都跑一遍构建是纯浪费。

**Independent Test**: 单独提交一处 `docs/` 或 `*.md` 改动并推送，确认没有新的流水线运行记录。

**Acceptance Scenarios**:

1. **Given** 提交只改 `*.md` 文件，**When** 推送，**Then** 不产生流水线运行
2. **Given** 提交同时改了 `.md` 与 `.vue`，**When** 推送，**Then** 流水线正常运行

---

### User Story 5 - 每次成功构建留下可核对的产物 (Priority: P3)

每次流水线成功后，`dist/` 可以被下载下来，用于核对线上跑的到底是哪一版。

**Why this priority**: 线上是 `git push` 到 bare repo 后由 hook 部署，没有版本戳。出问题时无法判断线上那份 dist 是不是最后一次构建的那份。

**Independent Test**: 在一次成功的运行页面下载产物，解压后确认包含 `index.html` 与 `assets/`。

**Acceptance Scenarios**:

1. **Given** 流水线全绿，**When** 打开该次运行页面，**Then** 可以下载构建产物
2. **Given** 流水线失败在构建之前的步骤，**When** 查看运行页面，**Then** 没有可下载产物（不产出半成品）

---

### Edge Cases

- **新增依赖但忘记提交锁文件**：安装步骤必须失败，而不是静默用旧锁文件装出「能跑」的树。
  这是本仓库已知隐患（`dayjs` 被 `Dashboard.vue` 直接 import，却不在 `package.json`）。
- **Node 版本漂移**：本地 22、CI 固定同一主版本。README 声明的下限（>=18）与 CI 实际版本不一致时，以 CI 为准并更新 README。
- **单测误依赖真实后端**：任何新测试都不得请求 5173/8000，否则 CI 必红。测试必须自给自足（mock 网络层）。
- **存量违规导致门禁首次即红**：接流水线前必须先把存量清零，否则第一天就在红线上，之后没人再看。
- **既有的 >500 kB chunk 告警**：这是已知技术债（constitution §三），**构建仍算通过**，不得因为告警判红。
- **个人仓库无强制分支保护**：CI 红不阻止推送。因此「红」必须足够显眼（运行失败 + README 徽章），而不是指望流程卡点。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 仓库 MUST 在每次 `main` 分支推送时自动运行一条流水线，无需人工点击
- **FR-002**: 流水线 MUST 严格按「锁文件安装 → 规范检查 → 单元测试 → 生产构建」顺序执行，任一环节失败即终止后续环节
- **FR-003**: 依赖安装 MUST 使用锁文件精确安装，锁文件与 `package.json` 不一致时 MUST 失败
- **FR-004**: 规范检查 MUST 覆盖 `src/` 下全部 `.js` 与 `.vue` 文件，并做到**存量零违规**（不允许用警告代替失败）
- **FR-005**: 单元测试 MUST 在无网络、无后端、无浏览器的环境下通过，且至少覆盖 API 层的请求构造与路由表的可解析性
- **FR-006**: 生产构建 MUST 产出可用的 `dist/`，构建成功后在运行页面提供可下载产物
- **FR-007**: 密钥扫描 MUST 扫描完整提交历史，并作为**独立 job**存在，其失败 MUST 使整体结论为失败
- **FR-008**: 仓库 MUST 提供一条本地预检命令，其检查项与 CI 完全同源（同一组命令、同一份配置）
- **FR-009**: 只修改 `*.md` 的推送 MUST 不触发流水线
- **FR-010**: `README.md` MUST 展示流水线状态徽章，并给出本地预检命令与 CI 各步骤的对应说明
- **FR-011**: `AGENTS.md` MUST 在「常用命令」与质量门章节登记本地预检命令，使后续接手的模型知道有这道门
- **FR-012**: 流水线 MUST NOT 包含任何部署/上线动作（本次明确不做 CD）

### Key Entities

- **检查项（Gate）**：一道可独立判定成败的门禁，含名称、命令、失败后果。本次共 4 道主检查 + 1 道密钥扫描。
- **本地预检命令**：与 CI 同源的单一入口脚本，退出码即结论。
- **产物（Artifact）**：一次成功构建的 `dist/` 快照，含保留期限。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一次普通推送后 **6 分钟内**得到最终结论（首次运行含冷缓存，此后应稳定在 3 分钟内）
- **SC-002**: 本地预检的检查项与 CI 一一对应，**无任何一项只在 CI 或只在本地执行**
- **SC-003**: 接入时全库规范违规数从当前存量降到 **0**，且此后每次推送都维持 0
- **SC-004**: 单元测试数量 ≥ **15 条**，全部可在无外部依赖环境下运行，本地与 CI 结果一致
- **SC-005**: 故意制造的三类故障（语法错误 / 规范违规 / 测试失败）**各能独立使对应步骤变红**，验证记录留档在 `tasks.md`
- **SC-006**: 纯文档推送 **0 次**流水线运行
- **SC-007**: 后续接手者只读 `AGENTS.md` 就能找到并运行预检命令（以「文档里出现的命令逐条真跑一遍」为验收方式）

## Assumptions

- 代码托管在 GitHub（`origin` 指向 `Chunxia-zzz/TraderAnalysisFrontend`），流水线直接使用 GitHub 提供的运行环境，**不引入自托管 runner**
- 仓库为个人项目，无强制合并审批；CI 作为「体检」而非「关卡」，因此强调结论可见性
- 现有部署方式（`git push` 到 `47.106.175.84` 的 bare repo）保持不变，本次不触碰服务器
- 本地开发环境为 Windows + Node 22，CI 使用同一 Node 主版本，避免版本差异掩盖问题
- 现有的 `scripts/smoke-*.mjs` 继续作为本地验收手段，**不纳入 CI**
- 已知的 `chunks > 500 kB` 告警、`dayjs` 未显式声明等属于既存技术债，本次**不修业务代码**，只保证它们不阻塞门禁
